   265→Known limitations and security concerns:
   266→1. **PgLite is NOT a real PostgreSQL server.** Single-process,
   267→   single-connection. SERIALIZABLE transactions have no real concurrent
   268→   contention under PgLite. `pg_advisory_lock` semantics differ. All
   269→   Phase 1 tests pass against PgLite ONLY. Real PostgreSQL integration
   270→   tests are mandatory before production deployment. PgLite must NEVER
   271→   be deployed as the production database on Netlify.
   272→2. **PgLite + Next.js 16 Turbopack dev-server interop.** Direct
   273→   `new PGlite()` calls from the dev-server's React Server Components
   274→   fail with one of:
   275→   - "TypeError: The path argument must be ... URL. Received an
   276→     instance of URL" (Turbopack intercepts fs.readFile and rejects
   277→     URL objects PgLite passes for `pglite.wasm`, `initdb.wasm`,
   278→     `pglite.data`).
   279→   - "PGlite failed to initialize properly" even after pre-loading
   280→     WASM modules + fsBundle (Postgres WASM `callMain` returns non-alive
   281→     status — root cause not isolated in Phase 1).
   282→   The adapter pre-loads WASM modules and fsBundle from STRING paths to
   283→   bypass the URL error (the URL error IS resolved). The remaining init
   284→   failure is left unresolved for Phase 1 scope; the Phase 1 page is
   285→   STATIC (does not query the DB from the dev server) and the
   286→   foundation is verified by integration tests run via `bun test` (Bun
   287→   runtime works fine with PgLite) plus `bun run db:migrate`/`db:seed`.
   288→   Phase 2 should either: (a) run DB queries via API routes invoked
   289→   through a separate worker process, (b) investigate the PgLite init
   290→   failure under Turbopack in more depth, or (c) accept that the dev
   291→   server uses static mock data while real DB queries happen through
   292→   API endpoints tested via integration tests.
   293→3. **Stale Postgres lock files.** If a PgLite process exits abruptly
   294→   (e.g., Turbopack hot-reload), `postmaster.pid` may remain and block
   295→   the next instance. The adapter's `cleanStaleLockFiles` removes them
   296→   in dev/test before constructing PgLite. This is dev-only behavior;
   297→   production uses `pg` and never calls this.
   298→4. **Auth secrets in `.env`.** Dev placeholders are accepted (≥32
   299→   chars) so first-run works. Production refuses placeholders and
   300→   requires real secrets (env.ts production-only check). The `.env`
   301→   file is gitignored.
   302→5. **Initial admin provisioning.** The `INITIAL_ADMIN_EMAIL` env var
   303→   is read but NOT yet used — the provisioning script is Phase 2 scope.

   310→7. **CSRF.** Not yet implemented (Phase 2 scope). The `CSRF_SECRET` and

   371→- Re-enabled a genuine live DB health check in `src/app/page.tsx` with

   373→- First fresh request: surfaced the REAL error message:
   374→    `TypeError: The "path" argument must be of type string or an instance
   375→    of Buffer or URL. Received an instance of URL`
   376→  — confirming the value IS a URL instance (per Node's
   377→  `determineSpecificType` formatter), but `instanceof URL` returns false
   378→  because Turbopack bundles some modules in a different realm with a
   379→  different `URL` constructor. Cross-realm `instanceof` fails.
   380→- Added a diagnostic monkey-patch (URL→file-path via duck typing on
   381→  `.href`/`.protocol`/`.pathname`) to capture the actual URL string.
   382→  This produced the CRITICAL piece of evidence:
   383→    `Cannot convert non-file URL to path (protocol=,
   384→     href=/_next/static/media/pglite.4bea2204.data)`
   385→  — Turbopack treats `pglite.data` as a STATIC ASSET: copies it to
   386→  `.next/static/media/pglite.<content-hash>.data` and gives PgLite an
   387→  HTTP path (no file at that path on disk). PgLite's default loader
   388→  calls `fs.promises.readFile(<http-url>)` which can NEVER work.
   389→- Root cause confirmed: NOT a realm mismatch alone, NOT a PgLite bug —
   390→  Turbopack's static-asset handling for `.wasm` and `.data` files
   391→  produces URLs that PgLite's default `fs.readFile`-based loader cannot
   392→  use. The same issue affects `pglite.wasm`, `initdb.wasm`, and
   393→  `pglite.data`.
   394→- Applied the evidence-based fix: use PgLite's DOCUMENTED `PGliteOptions`
   395→  (`pgliteWasmModule`, `initdbWasmModule`, `fsBundle`) to pre-load all
   396→  three artifacts from STRING file paths (via `fs.readFileSync`,
   397→  resolving the dist directory from `process.cwd()` because Turbopack's
   398→  static analyzer cannot resolve subpath exports not in the package's

  1035→Security design summary:
  1036→
  1037→- **Argon2id password hashing**: PHC-format hash stored in
  1038→  `user_credentials.argon2id_hash`. Params: 19 MiB memory, 2 iterations,
  1039→  parallelism=1. Never logged. Never returned in API responses.
  1040→- **Opaque session tokens**: 256-bit random tokens (base64url). Only
  1041→  SHA-256 hash stored in `sessions.token_hash`. DB breach does NOT
  1042→  expose live sessions. Cookie is HttpOnly (JS cannot read).
  1043→- **CSRF protection**: Stateless HMAC-tied double-submit.
  1044→  `csrf = HMAC(session_token, CSRF_SECRET)`. Three-way match: HMAC
  1045→  computed from session cookie == CSRF cookie == X-CSRF-Token header.
  1046→  Secured against CSRF and CSRF cookie fixation. No DB cost.
  1047→- **Rate limiting**: DB-backed (works across serverless instances).
  1048→  Per-email (5/15min) + per-IP (20/15min) + per-user account lock
  1049→  (5 failures → 15-min lock). NOT in-memory.
  1050→- **Forced password change**: `must_change_password=true` on provisioned
  1051→  accounts. Enforced by `requireNotMustChangePassword()` which throws
  1052→  MUST_CHANGE_PASSWORD (HTTP 426) on EVERY protected handler. The
  1053→  change-password endpoint is the only exempt endpoint (it IS the
  1054→  escape hatch).
  1055→- **Role + academy authorization**: `requireRole(principal, role,
  1056→  academyId?)` and `requireAcademyMembership(principal, academyId)`.
  1057→  Cross-academy access fails even with a valid UUID from another
  1058→  academy. Never trusts client-supplied role/academy ID.
  1059→- **Initial admin provisioning**: `scripts/provision-admin.ts` reads
  1060→  `INITIAL_ADMIN_EMAIL` from env. No public endpoint. Creates user
  1061→  with `must_change_password=true` (forces fresh password on first
  1062→  login). Idempotent — does NOT overwrite existing passwords.
  1063→- **Error sanitization**: All errors go through `toSafeResponse()` which
  1064→  returns `{error:{code, message, detail?}}`. Never includes SQL, stack
  1065→  traces, password hashes, or session tokens. Generic login failure
  1066→  message prevents user enumeration.
  1067→- **Cookie security**: HttpOnly (session), Secure in production, SameSite
  1068→  =Lax, Path=/. CSRF cookie is NOT HttpOnly (client JS must read it)
  1069→  but uses SameSite=Lax + the HMAC tie for security.

  1072→1. **PgLite ≠ real PostgreSQL server** — single-process, no real
  1073→   concurrency. SERIALIZABLE isolation has no real contention under

  1075→2. **`pg` adapter not yet implemented** — production deployment is

  1395→=== 1. CSRF on password changes ===
  1396→
  1397→FINDING: The change-password endpoint was EXEMPT from CSRF protection.
  1398→The original rationale was: "the user may be forced here immediately
  1399→after login (before they have a usable CSRF token in their cookie)."
  1400→
  1401→This rationale was INCORRECT. The login route sets BOTH cookies on
  1402→every successful login:
  1403→  - `futsal_session` (HttpOnly) — the raw session token
  1404→  - `futsal_csrf` (NOT HttpOnly) — the CSRF token
  1405→
  1406→After login, the client has the CSRF cookie and can read it from
  1407→`document.cookie` (because it's NOT HttpOnly). The client can submit
  1408→it in the `X-CSRF-Token` header. A forced-password-change user (who
  1409→just logged in) DOES have a CSRF token available immediately.
  1410→
  1411→The current-password verification is proof of IDENTITY (the requester
  1412→knows the current password). CSRF verification is proof of ORIGIN
  1413→(the request came from the same site that set the cookies). These are
  1414→DIFFERENT security controls; both are required.
  1415→
  1416→FIX: Enforced CSRF on the change-password endpoint. The route now:
  1417→  1. Parses + validates the body (422 on invalid)
  1418→  2. Extracts the principal (401 if not authenticated)
  1419→  3. Verifies CSRF (403 if missing/invalid) — THREE-WAY match:
  1420→     HMAC(session_token, CSRF_SECRET) == CSRF cookie == X-CSRF-Token header
  1421→  4. Calls `changePassword` (which includes current-password verification
  1422→     + transactional other-session revocation)
  1423→  5. Returns the updated principal
  1424→
  1425→The session-revocation behavior is PRESERVED: the current session
  1426→stays valid, all OTHER sessions for the same user are revoked
  1427→(transactionally), other users' sessions are never touched.
  1428→
  1429→Updated the AuthShell client component to include the `X-CSRF-Token`
  1430→header in the change-password fetch request (reading the CSRF cookie
  1431→from `document.cookie`, same as the logout handler).

  1518→
  1519→WHY `X-Real-IP` IS TRUSTED (in the sandbox):
  1520→  - Caddy's `header_up` directive REPLACES the header value. Even if a
  1521→    client sends `X-Real-IP: 1.2.3.4`, Caddy overwrites it with
  1522→    `{remote_host}` (the actual TCP remote IP connecting to Caddy).
  1523→  - `{remote_host}` is Caddy's placeholder for the immediate TCP peer.
  1524→    Since Caddy is the edge (no upstream proxy in front), this is the
  1525→    real client IP.
  1526→  - Same for `X-Forwarded-For` — Caddy replaces (not appends to) the
  1527→    client-supplied value.
  1528→  - The app's `getClientIp()` prefers `X-Real-IP` (overwritten by Caddy),
  1529→    then `X-Forwarded-For` (also overwritten by Caddy). Both are
  1530→    trustworthy in the sandbox.
  1531→
  1532→CAN THE APP BE REACHED DIRECTLY (bypassing Caddy)?
  1533→  - In the sandbox: NO. Port 81 (Caddy) is the only externally accessible
  1534→    port. Port 3000 (Next.js dev server) binds to localhost only.
  1535→    `ss -tlnp` confirms only `*:81` is listening externally.
  1536→  - An attacker cannot bypass Caddy to reach port 3000 directly and
  1537→    spoof IP headers.
